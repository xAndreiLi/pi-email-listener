### The Cloudflare drop can be provisioned from one `wrangler login` plus one `wrangler deploy`, except for onboarding the domain itself. Wrangler 4.113.0+ (September 2026) creates Email Routing rules from a top-level `addresses` field on deploy, auto-provisions KV/D1 bindings declared without ids, and its OAuth login requests every scope in its catalog by default — including `email_routing:write`. Enabling Email Routing on a zone (POST /zones/{zone_id}/email/routing/dns, which adds and locks the MX and SPF records) accepts only the `Zone Settings Write` permission, which wrangler's OAuth catalog does not carry (it has `zone:read`), so the one-time 'Onboard Domain' step is expected to remain a dashboard click. Unverified: whether `email_routing:write` also covers enabling, and whether a Worker-only rule needs a verified destination address.
Kind: fact
Evidence:
- source: https://developers.cloudflare.com/email-service/configuration/email-routing-addresses/ — "This feature requires Wrangler 4.113.0 or later... When you run wrangler deploy or wrangler triggers deploy, Wrangler reconciles the Email Routing rules for the addresses you listed. It adds rules for new entries"
- source: https://developers.cloudflare.com/changelog/post/2026-09-04-email-routing-rules-wrangler/ — "You can now manage Email Routing rules that route emails to Workers from your Wrangler configuration."
- source: https://developers.cloudflare.com/workers/wrangler/configuration/ — "Wrangler can automatically provision resources for you when you deploy your Worker without you having to create them ahead of time. This currently works for the following resources: KV, R2, D1"

### AgentMail lets a program create a receive-only agent inbox with one unauthenticated call — POST https://api.agentmail.to/v0/agent/sign-up with a `username` returns an `inbox_id` (`<username>@agentmail.to`) and an `api_key` — and that inbox is readable over IMAP at imap.agentmail.to:993 with the inbox address as the user and the API key as the password. This package's existing imap source could therefore read it with no new adapter, and setup would need no human sign-up, card, domain, app password or OAuth. Without a human email the inbox cannot send to anyone, which matches the no-send boundary, but a lost key cannot be recovered. Unverified organizations are denied only api_key_create, list entries, pods and app_connect — reading is not restricted. Free tier: no card, 3 inboxes, 3,000 emails/month, 3 GB; the 24-hour message expiry is an opt-in enterprise policy, off by default. Not yet run live.

### AgentMail drops inbound mail whose SPF, DKIM or DMARC explicitly fails, without a bounce to the sender, and stores mail it judges spam outside INBOX (an IMAP Spam folder, also excluded from API listings by default). A watcher on INBOX alone — which is what /email-setup writes — therefore misses spam false positives silently, and a correspondent whose domain authentication is broken can believe a message was delivered. Cloudflare rejects the same authentication failures, but at SMTP time.
Kind: gotcha
Evidence:
- source: https://docs.agentmail.to/knowledge-base/inbound-emails-missing.md — "Emails dropped due to failed authentication are rejected without a bounce-back to the sender. The sender's mail server may still report successful delivery"

### Cloudflare Email Routing does not spam-filter inbound mail, but it rejects mail that fails both SPF and DKIM, mail that fails according to the sender's DMARC policy, and senders on realtime block lists (554). Everything else reaches the Worker. Inbound messages over 25 MiB are rejected, and a domain carries at most 200 routing rules. This answers INTAKE §7 question 4: an authenticated stranger's spam reaches the agent, which is consistent with no gate.
Kind: fact
Evidence:
- source: https://developers.cloudflare.com/email-service/reference/postmaster/ — "The email must either pass SPF or be correctly signed with DKIM. Emails that fail both checks are rejected. ... For Email Routing, incoming emails are rejected if they fail authentication according to the sender's DMARC policy."
- source: https://developers.cloudflare.com/email-service/reference/postmaster/ — "For Email Routing, inbound mail from senders on RBLs is rejected with an SMTP error similar to: 554"
- source: https://developers.cloudflare.com/email-service/platform/limits/ — "Inbound message size | 25 MiB | Messages larger than this are rejected ... Routing rules per domain | 200"

### Surviving a reboot buys pre-fetching only, not durability. The wake needs an open pi session; any session start relaunches the fetcher when service.autoStart is set; and the IMAP source resumes from lastUid+1 with no cap (the 50-message cap applies only to a first pass with no cursor). So mail that arrives while the machine is off waits on the server and is fetched in full by the next session. The same holds for any durable drop (a Cloudflare KV store, an AgentMail inbox). A scheduled task or systemd unit is therefore not on the path to one-click setup.
Kind: architecture

### Reading Gmail through the user's own Apps Script web app avoids app passwords, but it is not a one-click route. Google documents no verification exemption for Apps Script, so a fresh copy shows the 'unverified app' screen before consent. Setup is copy the script, deploy it as a web app, authorize through that warning, then paste the URL. Consumer quotas are ample for polling: 20,000 email reads a day, and no stated cap on web-app executions, though all quotas are subject to change without notice. It is a fallback for someone who must stay on Gmail after app passwords are refused, not a default.
Kind: fact
Evidence:
- source: https://support.google.com/cloud/answer/7454865 — "If a new Apps Script script requests OAuth access to data that belongs to consumers or users in other domains, the "unverified app" screen might display before the OAuth consent flow."
